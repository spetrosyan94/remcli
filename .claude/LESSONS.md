# Уроки и паттерны ошибок

Этот файл обновляется после каждой коррекции от пользователя. Проверяй в начале каждой сессии.

---

## Формат записи

```
### [Дата] Краткое описание
- **Ошибка**: что пошло не так
- **Причина**: почему это произошло
- **Правило**: как предотвратить повторение
```

## Записи

(пока пусто — обновляется по мере работы)

### [2026-07-02] Структура модулей: константы и типы — в отдельных файлах
- **Ошибка**: conciergeService.ts собрал в себе всё — константы (WHITELISTED_AGENTS, CONCIERGE_SYSTEM_PROMPT, лимиты), типы/интерфейсы и логику; пользователь указал на нарушение
- **Причина**: агенты-реализаторы кладут всё в один файл «для самодостаточности», промты волн не требовали разнесения
- **Правило**: при создании нового модуля из нескольких сущностей — constants.ts (константы, промты, лимиты), types.ts (интерфейсы/типы), сервисный файл (логика). В промты тиммейтам-реализаторам включать это требование явно (ссылка на core-standards)

### [2026-07-04] Агенты не списывают найденные ошибки как чужие
- **Ошибка**: агент нашёл падающий typecheck и сообщил, что ошибки «существующие/не связаны с моей логикой», не исправив и не эскалировав их как отдельную работу.
- **Причина**: промпты агентам ограничивали ownership файлами задачи, но не задавали обязательный протокол для обнаруженных блокеров проверки.
- **Правило**: агент не имеет права списывать найденные ошибки как «не мои» и молча завершаться. Если ошибка в зоне компетенции/пакете агента — он обязан исправить её. Если ошибка вне текущего ownership — обязан явно сообщить лиду, а лид делегирует отдельному агенту. После фикса адверсиальный критик повторно проверяет результат.

### [2026-07-04] Критикам с проверками нужен Bash-доступ
- **Ошибка**: адверсиальные критики были запущены как специализированный `code-reviewer`, у которого в этом harness нет Bash; из-за этого они не могли запускать typecheck/test/build и писали «нет shell/Bash-инструмента».
- **Причина**: выбран agent type по названию роли, а не по требуемым инструментам для задачи.
- **Правило**: если критик должен подтверждать проверки командой (`npm test`, `typecheck`, `build`, git status, diff), запускать его как `claude` или `general-purpose` с ролью адверсиального критика и явным требованием использовать Bash. `code-reviewer` использовать только для read-only ревью, где shell не нужен.

### [2026-07-04] Тестеры и критики проверяют основной репозиторий
- **Ошибка**: тестеры и адверсиальные критики запускались в отдельных worktree, из-за чего проверяли не основной working tree; затем лидер копировал diff и был вынужден повторять проверки.
- **Причина**: worktree использовался по умолчанию для всех агентов, хотя лидерская схема предполагает принятие изменений в основном репозитории.
- **Правило**: разработчики, тестеры и критики должны работать напрямую в основном репозитории, если нет явной причины изолировать конфликтующие параллельные реализации. Лидер смотрит diff и принимает решение о коммите/пуше. Worktree использовать только для безопасного параллелизма потенциально конфликтующих вариантов; финальные проверки всегда запускать в основном репозитории.
