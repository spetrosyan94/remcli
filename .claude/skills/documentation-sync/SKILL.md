# Синхронизация документации

## Когда применять

После завершения ЛЮБОЙ задачи (фича, ТЗ, баг-фикс) ОБЯЗАТЕЛЬНО:

1. Проверить документацию сервиса/CMS в папке `/_docs` или `docs/`
2. Если метод новый — создать документацию
3. Если метод изменён — обновить документацию

## Что проверять

| Аспект | Действие |
|--------|----------|
| Структура метода | Сравнить с логикой в коде |
| Параметры | Проверить типы, обязательность, defaults |
| Ответ | Проверить формат и поля ответа |
| Ошибки | Проверить коды ошибок |
| Примеры | Обновить примеры если логика изменилась |

## Формат документации

Документация ДОЛЖНА соответствовать формату других методов в проекте:
- Смотреть примеры в той же папке `docs/` или `/_docs`
- Не выдумывать новый формат
- Копировать структуру существующих методов

## Типы документации

### API документация
- OpenAPI/Swagger спецификация
- Описание endpoints
- Request/Response schemas
- Коды ошибок

### Схемы БД
- Описание таблиц
- Связи между таблицами
- Индексы
- Миграции

### Бизнес-логика
- README с описанием логики
- Комментарии в коде (только "почему", не "что")
- Flowcharts для сложных процессов

## Чеклист после завершения задачи

- [ ] Документация существует?
- [ ] Параметры соответствуют коду?
- [ ] Ответ соответствует коду?
- [ ] Коды ошибок актуальны?
- [ ] Примеры работают?
- [ ] README обновлён (если нужно)?
