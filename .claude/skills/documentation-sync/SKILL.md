# Синхронизация документации

## Почему это важно

Устаревшая документация хуже отсутствующей — она вводит в заблуждение. Разработчик доверяет docs, пишет код по ним, а он не работает. Стоимость: часы отладки вместо минут чтения актуальной документации.

Этот skill напоминает проверять документацию после каждого изменения кода.

При напоминании о документации всегда объясняй **почему** это важно: устаревшая документация вводит в заблуждение, разработчик тратит часы на отладку кода, написанного по неактуальным docs. Не просто показывай чеклист — объясни ценность каждого пункта.

---

## Когда применять

После завершения любой задачи проверь:

1. Существует ли документация для затронутого кода?
2. Если да — соответствует ли она текущей реализации?
3. Если нет — нужна ли она? (публичные API — да, внутренние утилиты — обычно нет)

---

## Что проверять

| Аспект | Действие |
|--------|----------|
| Структура метода | Сравнить с логикой в коде |
| Параметры | Проверить типы, обязательность, defaults |
| Ответ | Проверить формат и поля ответа |
| Ошибки | Проверить коды ошибок |
| Примеры | Обновить примеры если логика изменилась |

---

## Типы документации

### API документация
- OpenAPI/Swagger спецификация
- Описание endpoints, request/response schemas
- Коды ошибок

### Схемы БД
- Описание таблиц и связей
- Индексы
- Миграции (описание что изменилось)

### Бизнес-логика
- README с описанием модуля
- Комментарии в коде (только "почему", не "что")
- Flowcharts для сложных процессов

---

## Формат

Документация должна соответствовать формату, уже принятому в проекте:
- Смотри примеры в `docs/`, `/_docs`
- Не выдумывай новый формат — копируй структуру существующих

## Чеклист после завершения задачи

- [ ] Документация существует?
- [ ] Параметры соответствуют коду?
- [ ] Ответ соответствует коду?
- [ ] Коды ошибок актуальны?
- [ ] Примеры работают?
- [ ] README обновлён (если нужно)?
