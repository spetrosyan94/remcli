# Универсальные стандарты разработки

Базовые правила для любого проекта. Не содержит domain-specific стандартов — за ними обращайся к:
- Бэкенд, API, JWT, валидация → skill `backend-standards`
- Фронтенд, UI, дизайн, эстетика → skill `frontend-standards`

## 2. Clean Code и SOLID

### Почему SOLID

Код без принципов быстро становится "большим комком грязи" — изменение одного места ломает другое, тесты невозможны, онбординг новых разработчиков занимает недели. SOLID решает это через изоляцию ответственности.

- **S** — Single Responsibility: один класс/функция — одна причина для изменения. Если описание функции содержит "и", она делает слишком много.
- **O** — Open/Closed: новое поведение добавляется расширением (новый класс, стратегия), а не правкой существующего кода. Снижает риск регрессий.
- **L** — Liskov Substitution: подтипы заменяют базовые типы без сюрпризов. Нарушение — когда `instanceof` проверки разбросаны по коду.
- **I** — Interface Segregation: клиент не зависит от методов, которые не использует. Много маленьких интерфейсов лучше одного "бога".
- **D** — Dependency Inversion: высокоуровневые модули зависят от абстракций, не от конкретных реализаций. Делает код тестируемым.

### Паттерны проектирования (применять по необходимости)

- Repository — для работы с БД
- Service — для бизнес-логики
- Factory — для создания объектов
- Strategy — для взаимозаменяемых алгоритмов
- Observer — для событий

### Чистый код

Почему: код читается в 10 раз чаще, чем пишется. Инвестиция в читаемость окупается на каждом code review и дебаге.

- Функции делают одну вещь
- Минимум вложенности (early return) — каждый уровень вложенности увеличивает когнитивную нагрузку экспоненциально
- Комментарии только для "почему", не "что" — код должен быть самодокументирующим
- DRY — избегать дублирования, но не ценой преждевременных абстракций (Rule of Three)
- ЗАПРЕЩЕНО: `// ...`, `// TODO` (без тикета), `// остальной код`, placeholder-комментарии

## 3. Нейминг

Почему это критично: плохие имена — главная причина "что этот код делает?" вопросов. Хорошее имя заменяет комментарий и документацию.

| Правило | Хорошо | Плохо |
|---------|--------|-------|
| Функции — глаголы | `getUserBalance`, `calculateBonus` | `userBalance`, `bonus` |
| Переменные — существительные | `userBalance`, `bonusAmount` | `get`, `calc` |
| Без аббревиатур | `transactionId`, `configuration` | `txId`, `cfg` |
| Общепринятые — можно | `id`, `url`, `api`, `db` | `identifier`, `uniformResourceLocator` |
| Boolean — вопрос | `isActive`, `hasAccess`, `canEdit` | `active`, `access`, `edit` |
| Массивы — множественное число | `users`, `orderItems` | `userList`, `orderItemArray` |
| Callbacks — on/handle | `onSubmit`, `handleClick` | `submit`, `click` |

```typescript
// ПЛОХО — приходится читать каждую строку чтобы понять смысл
const d = getData();
const r = calc(d.a, d.b);
if (r > t) { process(r); }

// ХОРОШО — понятно с первого взгляда
const userTransaction = getLatestTransaction();
const bonusAmount = calculateBonusFromTransaction(userTransaction.sum, userTransaction.type);
if (bonusAmount > minimumBonusThreshold) {
  applyBonusToUserAccount(bonusAmount);
}
```

## 4. Запрет магических чисел и строк

Почему: магическое число "86400000" ничего не говорит читателю. Константа `MS_IN_DAY` — говорит. Плюс при изменении значения правишь в одном месте.

```typescript
// ПЛОХО
if (status === 1) { ... }
if (role === 'admin') { ... }
setTimeout(() => {}, 86400000);

// ХОРОШО
const EStatus = { ACTIVE: 1, INACTIVE: 0 } as const;
const ERoles = { ADMIN: 'admin', USER: 'user' } as const;
const MS_IN_DAY = 24 * 60 * 60 * 1000;

if (status === EStatus.ACTIVE) { ... }
if (role === ERoles.ADMIN) { ... }
setTimeout(() => {}, MS_IN_DAY);
```

Все значения выносить в: `constants/`, `config/`, `types/enums/`

## 5. Environment Variables

### Структура .env файлов

- `.env.example` — шаблон с комментариями (БЕЗ секретов, в git)
- `.env` — локальные переменные (в .gitignore)

### Формат

```bash
# ============================================================================
# Database Configuration
# ============================================================================
DATABASE_URL=postgresql://user:password@localhost:5432/app

# ============================================================================
# Application Configuration
# ============================================================================
NODE_ENV=development
PORT=3000
LOG_LEVEL=debug

# ============================================================================
# Frontend Configuration (VITE_ prefix обязателен)
# ============================================================================
VITE_API_URL=http://localhost:3000/api/v1
```

- Секции разделять комментариями
- Фронтенд переменные с префиксом `VITE_`
- Валидировать env через zod при старте приложения (пример → skill `backend-standards`, секция "Environment")
