# Границы безопасности P2P

Этот документ описывает фактические границы безопасности Remcli P2P. Он не
заменяет [протокол](protocol.md) и [форматы шифрования](encryption.md): здесь
зафиксированы модель угроз, гарантии и осознанные ограничения.

## Что защищает текущая схема

- QR-ссылка несёт pairing material только во fragment URL: он не уходит на
  сервер в HTTP-запросе.
- Pairing key не имеет автоматического срока жизни: daemon хранит его локально
  и использует тот же QR после рестарта. Он меняется только по явному действию
  пользователя `Rekey` (либо при утрате/повреждении локального pairing файла).
- `authSecret` выводит bearer для подключения, а `contentSecret` используется
  для зашифрованных пользовательских payload.
- Зашифрованные payload имеют проверку целостности: их нельзя незаметно
  изменить без ключа.
- Каждый изменяющий P2P-запрос, аутентифицированный bearer, несёт одноразовый
  request proof: HMAC-SHA512 от уже существующего `authSecret`, привязанный к
  версии протокола, транспорту, операции, request id, подписанному `expiresAt`
  и payload. Исключение — daemon-issued session runner с проверенным
  `runnerCredential`; он имеет более узкую session scope. Daemon принимает
  request id один раз до его подписанного expiry; replay cache очищается после
  expiry и ограничен по capacity, временно fail-closed пока все записи живы.

Последний пункт защищает от повторной отправки перехваченного bearer вместе с
ранее валидным запросом в пределах validity window, включая перенос
зашифрованного сообщения в другую сессию. Для него не меняются QR-формат,
алгоритмы шифрования или зависимости: используется уже существующий ключ
pairing и HMAC-SHA512.

Для JSON HTTP endpoint proof привязан к итоговому JSON body. `POST
/v1/voice/transcribe` принимает multipart: его proof намеренно использует
payload `null` и привязывает только операцию и request id, а не бинарный audio
stream. Поэтому upload становится одноразовым для bearer без `authSecret`, но
схема не заявляет хеширование или криптографическое связывание binary body.

## Что эта схема намеренно не обещает

Request proof не делает прямое `http://`-подключение безопасным в недоверенной
сети. Активный атакующий в LAN может подменить первую страницу до того, как
браузер прочитает fragment, и получить pairing material. Если ключ уже украден,
он способен вычислять корректные proof.

Поэтому:

- прямой LAN URL предназначен только для доверенной локальной сети;
- для внешней или недоверенной сети используйте `npm run start:tunnel`: туннель
  даёт HTTPS-транспорт;
- QR/pairing material нельзя отправлять в чаты, логи, issue-трекеры и
  скриншоты;
- request proof не предотвращает DoS, XSS на доверенном устройстве, компрометацию
  daemon/host или чтение данных после компрометации самого pairing key.

## Ротация ключа

`Rekey` меняет `authSecret` и отзывает удалённое управление со старого QR:
старый bearer и новые request proof больше не пройдут. `contentSecret`
сохраняется, чтобы не оборвать активные session runners. Это availability
trade-off, а не полный cryptographic erase: rekey не отзывает способность уже
скомпрометированного `contentSecret` расшифровать ранее перехваченный legacy
traffic.

Полная реакция на компрометацию QR должна быть отдельной операцией: ротация
обоих секретов с остановкой или перепривязкой active runners. До отдельного
design/security решения Remcli не выдаёт rekey за такую операцию.

## Границы шифрования

Зашифрованы пользовательские сообщения и поля, для которых клиент передал
encrypted record. Служебные идентификаторы, версии, последовательности,
маршрут/имя события и часть daemon runtime state могут оставаться открытыми,
потому что нужны серверу для маршрутизации и контроля конкурентности. Не
интерпретируйте P2P store как полностью зашифрованный снимок всего daemon.

## Проверки при изменении протокола

Для каждого нового изменяющего P2P endpoint/event нужны negative tests:

1. отсутствующий или неверный proof не вызывает handler/store side effect;
2. повтор того же proof/request id отклоняется до подписанного expiry, а новая
   корректная mutation принимается после очистки истёкшего cache window;
3. payload нельзя перенести между session, route или Socket.IO/HTTP transport;
4. корректный browser и runner flow продолжают работать;
5. в ошибках и логах нет bearer, pairing material или proof.

Детали заголовков/полей и canonical payload находятся в реализации и
[протоколе](protocol.md); они должны меняться одновременно с тест-векторами
web и CLI.
